## 3. 对抗性问题逐条回答（任务卡第 55–63 行，对抗性）

**Q1. 旧名是否真的在三处彻底消失？**
是。src/、tests/、dist/、README.md、package.json 五类文件分别 `git grep -nF 'windowsChromeCandidates'` 与 `'detectWindowsChrome'` 均**无命中**（src 两处均为空 exit；dist 两处均为空 exit；README/package 为空）。残留仅在 `docs/`（spec、suspended 协作稿、旧 plan）与 `CHANGELOG.md:77` 的历史叙述中出现——非 shipped 代码，非活声明。dist/ 作为构建产物已重编译，无旧名残留。

**Q2. `accessSync(X_OK)` 在 Windows 退化为 `F_OK`**——「显式值与探测复用同一判据」在 Windows 上是否实际弱于 Unix？是否使 B2 在 Windows 上仍存在第二条真相路径？
不是编码层 blocker。理由：(a) `resolveChromeExecutable` / `detectChrome` 在显式值与自动探测两条路径上共用同一个 `probe()`，已消除 cli.ts 旧实现「显式值零校验直通」的 B2 根因；(b) 即便 Windows 上 `accessSync` 退化为 `F_OK`，它仍是「路径存在且是文件」的判据——弱于 Unix 的「可执行位检查」，但**不是「不检查」**；退化只发生在「显式路径存在但不可执行」这种边界，(c) 本评审中 `cli.ts` 的早失败检查与 `deepseek-web.ts` 的 bridge 启动检查现已用同一判据，不存在「CLI 说存在 / bridge 说不存在」的两条真相。结论：B2 在 Windows 上已闭合；X_OK 退化属 spec §6 已声明的「未验证项」，README 已知限制（第 247 行）已警告 headless 默认关。非 blocker。

**Q3. `posixJoin` + 硬编码 `:` 分隔符** 是否处理所有边界（PATHEXT、空格路径、`~` 展开）？
部分边界受 spec §6 约束，但无 blocker：
- `:` 分隔符是 POSIX `PATH` 语义，仅用于 Linux 分支；Windows 分支用 `LOCALAPPDATA`/`PROGRAMFILES` 等固定 env，不碰 PATH 分隔符，无跨平台串味。
- 空格路径：测试 `tests/chrome-detect-cross-platform.test.ts:114` 用 `PATH: '/definitely/not/here'` 验证（Node `process.env.PATH` 以字符串持有，空格不需特殊处理），逻辑成立。
- PATHEXT：仅影响 Windows 下「无扩展名是否算可执行」的判定，本实现要求候选表给出**完整带扩展名路径**（`.exe`），不依赖 PATHEXT 推断，规避了该边界。
- `~` 展开：未做；spec §6 列为「未验证项」，README 已知限制（第 247 行、headless 段）已声明「非 Windows 实际可用性未经验证」。非 blocker，但建议实现轮在 spec §6 #6 补一行明确「不展开 `~`」。

**Q4. Linux/macOS 分支真的能在 Windows 宿主上被测吗？**
诚实边界，非缺陷。测试只注入 `platform` 参数断言**候选表构造与分派顺序**（如 `chromeCandidates({}, 'linux')` 返回固定 2 条、`'darwin'` 返回 4 条），**不断言宿主探测结果**（spec §6 不可验证项明确：Windows 宿主上 Linux PATH 扫描分支无法用真实文件系统验证）。测试边界已在测试文件注释与 spec §6 中声明。作者未谎称「平台逻辑已真机验证」。结论：可测性边界诚实，不掩盖。

**Q5. `package.json` description 与 README 的共享子串能否被「抄进注释里」满足而不改实质？**
不能，判据已防住。Acceptance #14 要求**两个真实子串**（`Windows 已实测` 与 `代码路径存在但未验证`）在 `package.json`（恰 1）与 `README.md`（≥ 1）都各自 ≥ 1 命中，且 README 实测 3 处（Tier 表引言 / 安装要求 / 已知限制）均为真实声明文本、非注释。注释里的复读不会让 `package.json` 出现命中，故无法用「抄进注释」绕过。`cli-args.ts:17` 的第三副本用的是略短语「路径未验证」（语义一致，措辞略有差异，见 §5 偏差 1），亦非注释粉饰。

**Q6. README Tier 三级表是否过度承诺？**
否。Tier 1 = Windows 已实测；Tier 2 = 桌面 Linux/macOS「代码路径已存在·未验证」「无真机验证」「能否实际拉起 Chrome 未知」；Tier 3 = headless/Docker/WSL「不承诺」「物理上跑不通首登」。没有任何一句暗示 macOS 可用而未声明未验证。spec §6 的「未验证」立场在 README 第 22、237 行被复述。无过度承诺。

**Q7. 删 `os` 字段后 macOS 用户安装成功但首登大概率失败**——更诚实，还是把复杂度转嫁给用户？
更诚实，但需配套文档。删除 `os` 字段把「安装被拒」的硬墙换成「安装可成、首登未知」的软约束，与 spec §1.1「放开限制 + 扩充探测 + 诚实标注」哲学一致。代价是 macOS 用户会先装上再在首登时撞墙——但 README 第 237 行已知限制已写明「实际可用性未经验证」「headless 环境首登流程不成立」，属「已知限制前置披露」而非隐藏。建议实现轮在 `npm install` 后给一条 postinstall 提示（非阻塞），把「macOS 未验证」前置到安装期；当前虽未做，但不影响 PASS（spec §1.2 明确「三平台真机验证」是非目标）。
