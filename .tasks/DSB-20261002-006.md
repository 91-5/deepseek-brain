## Context

`deepseek-brain` 是把 DeepSeek 网页版包装成 OpenAI 兼容接口的 shim（监听 `127.0.0.1:8790`），
采用**懒启动**：进程起来不拉 Chrome，只在首个 chat 请求时启动。

`bf3e2d8` 想让它能作为**长期常驻后台服务**可靠运行，修三个问题：

1. **Chrome 异常退出后 shim 永久砖化**（最严重）：puppeteer 的 `browser`/`page` 对象在
   Chrome 崩溃/被关窗/休眠回收时**不会自动置 null**，只变成指向死进程的陈旧句柄。于是
   `startBridge()` 的 `if (browser) return` 与 `generate()` 的 `if (!page)` 双双早退
   → shim 永久 502，只能手动重启进程。
2. **`/health` 把三种状态压成一个信号**：懒启动冷态被误报成 `login_required`，
   运维探针无法区分「该等待」「该重连」「该去登录」。
3. **无常驻机制**：需手动 `node dist/cli.js`，进程挂在调用者 shell 生命周期上。

## Review questions

1. **`isConnected()` 的探测时机是否正确？** 它被放在 `startBridge()` 的早退判断和
   `generate()` 的触发条件里。若 Chrome 处于「启动中尚未连上」的状态，
   `isConnected()` 返回 false 会否导致重复 `launch()`？`starting` promise 的幂等锁
   是否足以覆盖这个窗口，还是需要额外状态（如 `launching` 标志）？
2. **显式 null 收窄（`if (!page) return bridge_idle`）是否掩盖了真实故障？**
   `launch()` 中途失败时 browser 已连上而 page 为 null，该状态归入 `bridge_idle`
   意味着探针会一直等下去而不是报错。是否应区分「正在启动」与「启动失败」？
3. **`/health` 的消费者兼容风险。** 新增状态值 `bridge_idle` 是加法，但无法阻止第三方
   读到未知值。`Health` 类型是导出的（`deepseek-brain/core` 子路径），是否有下游会做
   穷尽 switch 而在遇到新值时出错？是否该在 CHANGELOG 明确标为 breaking？
4. **本轮的判据是否够。** 8 条静态判据只能证明「代码里出现了某些串」与「测试没红」，
   **不能证明自愈行为真的发生**。真正的行为证据（A9）是手工实测的。这个缺口该由你判为
   condition，还是该补一条可自动化的行为测试（例如注入假 transport 模拟 browser 断开）？
5. **追溯审查的额外风险。** 这份代码已上线运行（推 `origin/main`）后才迎来首次评审，
   期间跨平台支持工作在其上叠加（`bf3e2d8..4d643c9` 共 29 files）。被审文件本身零改动，
