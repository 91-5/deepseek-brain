## Context

`deepseek-brain` 是把 DeepSeek 网页版包装成 OpenAI 兼容接口的 shim（监听 `127.0.0.1:8790`），
采用**懒启动**：进程起来不拉 Chrome，只在首个 chat 请求时启动。

本轮目标是让它能作为**长期常驻后台服务**可靠运行。此前实测发现三个问题：

### 问题 1：Chrome 异常退出后 shim 永久砖化（最严重）

Chrome 崩溃、被用户关窗、或休眠后被系统回收时，puppeteer 的 `browser` / `page`
对象**都不会自动置 null**——它们只是变成指向已死进程的**陈旧句柄**。于是：

- `startBridge()` 的 `if (browser) return` 一路早退（以为已启动）
- `generate()` 的 `if (!page) await startBridge()` 判定 `page` 非 null（以为已就绪）

两者叠加 → shim 永久 502，Chrome 再也不会被拉起，**只能手动重启进程**。

实测（修复前）：杀 Chrome 进程树 → `/health` 返回 `{"status":"error"}` →
发 chat 请求返回 **502** → 9222 始终未监听。

### 问题 2：`/health` 把三种状态压成一个信号

懒启动下 Chrome 尚未拉起时，`health()` 在 `page` 为 null 时返回 `login_required`。
这让运维探针**无法区分**：

| 真实处境 | 正确信号 | 修复前报成 |
|---|---|---|
| 刚启动，还没被叫醒 | 该等待 | `login_required` ❌ |
| bridge 起过但已死 | 该重连 | `error` ❌ |
| 页面在，账号真没登录 | 该去登录 | `login_required` ✓ |

这个误判在本次排查中真实把我带偏过：初次探测 `/health` 返回
`{"status":"login_required","loggedIn":false}`，我据此误判为「cookie 失效、需要手动登录」，
实际是懒启动的正常冷态。

### 问题 3：无常驻机制

shim 需手动 `node dist/cli.js` 启动，进程挂在调用者 shell 生命周期上，重启后无人拉起。

## Deliverables

### A. 自愈修复（`src/transports/deepseek-web.ts`）

- 新增 `isBridgeAlive()`：以 `browser.isConnected()` 为存活判据，探测本身吞异常
  （句柄已死时任何调用都可能抛，抛出必须等价于「死了」）
- 新增 `resetStaleBridge()`：清 `browser` / `page` / `chromeProc` / `chatSessionId`
- `startBridge()` 早退条件由 `if (browser) return` 改为 `if (isBridgeAlive()) return`；
  且在 `browser || page` 残留时先 `resetStaleBridge()` 再 launch
- `generate()` 的触发条件由 `if (!page)` 改为 `if (!isBridgeAlive())`
- `health()` 的判据同步改为 `isBridgeAlive()`，并补一处**显式 null 收窄**
  （`launch()` 中途失败时 browser 可能已连上而 `page` 仍为 null，该态归入
  `bridge_idle` 而非误报 `error`；同时让 TS 保住类型收窄）

### B. health 语义（`src/core/types.ts` / `src/server/http.ts` / 测试）

- `HealthStatus` 新增 `'bridge_idle'`
- `transport.health()` 与 `/health` 的 catch 降级分支均改为 `bridge_idle`
- 两条既有测试的断言与用例名同步（`expect(spy.calls).toEqual(['health'])` 守护
  「`/health` 绝不触发懒启动」这条不变量，**原样保留未动**）

### C. 常驻能力（`scripts/start-shim.cmd` / `scripts/install-autostart.ps1` / `.gitattributes`）

- `start-shim.cmd`：幂等启动器。端口已在监听则 exit 0 不起第二实例（两个 node 共用
  一个 `.chrome-profile` 会撞 Chromium profile 锁）；探测失败时**拒绝盲启**而非猜端口
  状态；日志按日期追加；`start /b` 脱离启动；轮询 `/health` 至多 30s 后退出
- `install-autostart.ps1`：默认 dry-run，两种方式
  - `-Method Registry`（默认）：写 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`，
    **无需管理员**
  - `-Method ScheduledTask`：`schtasks /create`，需管理员
- `.gitattributes` 新增 `*.cmd text eol=crlf` 与 `*.ps1 text eol=crlf`（见 Constraints）

### D. behaviour（可观测的端到端结果）

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 冷启动 `/health`（无 chat 请求） | `login_required` | `bridge_idle` |
| Chrome 被杀后 `/health` | `error` | `bridge_idle` |
| Chrome 被杀后发 chat 请求 | **502 永久失败** | 自愈：重拉 Chrome → `ok` |
| 热态 `/health` | `ok` | `ok`（不变） |

## Review questions

1. **`isConnected()` 的探测时机是否正确？** 它被放在 `startBridge()` 的早退判断和
   `generate()` 的触发条件里。若 Chrome 处于「启动中尚未连上」的状态，
   `isConnected()` 返回 false 会否导致重复 `launch()`？`starting` promise 的幂等
   锁是否足以覆盖这个窗口，还是需要额外状态（如 `launching` 标志）？
2. **显式 null 收窄（`if (!page) return bridge_idle`）是否掩盖了真实故障？**
   `launch()` 中途失败时 browser 已连上而 page 为 null，该状态归入 `bridge_idle`
   意味着探针会一直等下去而不是报错。是否应区分「正在启动」与「启动失败」？
3. **`/health` 的消费者兼容风险。** 新增状态值 `bridge_idle` 是**加法**，但
   PROTOCOL 无法阻止第三方读到未知值。老实说：`Health` 类型是导出的
   （`deepseek-brain/core` 子路径），是否有下游会做穷尽 switch 而在遇到新值时
   出错？是否该在 CHANGELOG 明确标为 breaking？
4. **本轮的判据是否够。** 8 条静态判据只能证明「代码里出现了某些串」与
   「测试没红」，**不能证明自愈行为真的发生**。真正的行为证据
   （杀 Chrome → 发请求 → 重拉）是作者手工实测的，无法在 CI 复现。
   这个缺口该由评审判为 condition，还是该补一条可自动化��行为测试
   （例如注入一个假 transport 模拟 browser 断开）？
