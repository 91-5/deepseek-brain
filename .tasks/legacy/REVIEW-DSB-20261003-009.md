## Review questions 逐条回答

**Q1 这条缝会腐坏吗？fake 只 stub 三个方法够不够？要不要加顺序断言？**

够，且反对加顺序断言。腐坏的三条路径都有人守：① 注入分支被删 → 测试走真实 `launch()` → 护栏让它在毫秒级红掉（A7 实测的就是这条失败路径本身）；② fake 被改成万能兜底 → F1-F5 的「响亮失败」设计会失效，但这要有人主动改 fake，且文件头注释明令禁止；③ 生产代码在 `openChatPage`/`startBridge`/`teardownBridge`/`health` 上动刀 → 三条断言全部直接受影响。关于 F4（page 赋值顺序）：把 `page =` 挪到 `goto` 之后其实是一种**同样合法的修法**——坏页不再产生，`isBridgeAlive() && page` 判据自然失活，下次 start 仍会重试，第三条断言（factoryCalls 1→2）在那种实现下照样绿。也就是说顺序断言锁死的不是「不腐坏」，而是「必须用当前这种修法」——这会把实现细节变成契约，反而加维护税。现状（锁不变量、不锁实现）是对的。

**Q2 护栏（CHROME_PATH 指向不存在路径）算不算测试逻辑污染？**

不算，它是本轮设计里第二有价值的东西（第一是注入缝本身）。理由：它不是断言的一部分，不改变任何被测行为的判定；它是**安全联锁**——把「测试不该有能力启动浏览器」这条物理事实固化下来。它同时是路径探测器：A7 的失败信息本身就证明了当时走的是哪条路。唯一 caveat 见 N1（delete vs 还原），一行的事。

**Q3 `ensureProfileDir` 被跳过，是对的还是掩盖了东西？**

是对的，但要诚实标注边界。它属于「起真浏览器」阶段，与坏页故障模式（browser 已连接、page 不可用）零交互；跳过它不影响本测试的判别力。但确实如卡所说，这个函数在注入路径下从未被执行——**它的正确性目前没有测试覆盖**。当前它只是一个 mkdir + 报错，风险低；若将来长出权限、磁盘满、路径冲突等逻辑，应该给它单独写单元测试，而不是往这条缝里塞。建议在 NOT_RUN 清单里补一行「ensureProfileDir 未被注入路径执行」。

**Q4 是否该补 live 测试？选三种收尾的哪个？**

选**窄缝 + live 门**（与作者倾向一致），理由：① F3（杀进程树 + close 3s 超时）是全卡最贵的未覆盖风险——「每次重试泄漏一个 Chrome，且各自持同一 profile 锁」是复合故障，窄缝在结构上永远测不到，NOT_RUN 声明再诚实也只是知情、不是覆盖；② live 门的成本几乎为零——`describe.runIf(LIVE_TEST==='1')` 的门已存在，加一个 describe 即可，CI 不受影响；③ live 测试的具体验收建议：真实 Chrome 下诱导导航失败，前后对比 `tasklist` 的 chrome.exe 进程数（断言零泄漏），并复测第二次 start 后仍无累积。**本轮 verdict 不以此为条件**——卡片的 NOT_RUN 声明诚实完整，交付范围与声明一致。

**Q5 给 `WebBridgeOptions` 加字段需要协议评审吗？**

不需要，独立确认成立。四条依据，全部实查：① `package.json` exports 仅 `.`、`./core`、`./package.json`，transports 文件不在其中，非公开 API；② 生产调用方不传时行为逐字不变——diff 核查仅三处改动：接口加可选字段、`const browserFactory = opts.browserFactory`、`launch()` 头部早退分支，option 为 undefined 时代码路径与改前完全一致；③ `Transport` 接口与 `HealthStatus` 联合类型未动（A1/A2 typecheck 全绿佐证）；④ 字段是可选加法，无迁移问题。属于仓内 API 面，卡内评审即可。

**Q6 隔离 worktree + junction 方法有没有引入新问题（如污染真实 node_modules）？**

方法成立，本轮实测无污染，但有一个**必须写下来的顺序性风险**：删 worktree 时若 junction 还挂着，`rm -rf` 会顺着链接递归删进真实 node_modules（Windows 上 junction 默认跟随遍历）。正确顺序是先 `cmd /c rmdir node_modules` 摘链接（只删链接本身），再 `git worktree remove --force`。本轮评审按此顺序执行并验证：真实 node_modules 完好（vitest 可执行在、115 包无损）。其余评估：① junction 复用依赖「worktree 与主仓依赖树一致」，本次基线 2ea90ad 与 HEAD 的 package.json 相同，成立；若将来被审基线依赖不同版本，junction 会静默用错依赖，届时应改为真实安装；② 测试本身 fs 副作用已受控（sessionsFile 指向 tmpdir、`openHome` 无 try/catch 不触发 dumpDom），无仓内写入；③ `git worktree add` 会在主仓 .git 写 worktree 元数据，已用 `git worktree remove` 干净移除。结论：方法比原地 checkout 严格更安全（本次事故的根因就是原地改写工作区），保留，补上顺序警告即可。
