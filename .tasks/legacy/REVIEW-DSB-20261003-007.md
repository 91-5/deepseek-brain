### Q1：starting 原子区是否仍然完好？

**代码分析**：

```typescript
async function startBridge(): Promise<void> {
  if (starting) return starting           // ① 外层幂等锁
  starting = (async () => {               // ② 同步赋值
    try {
      if (isBridgeAlive() && page) return  // ③ executor 内二次判复用
      if (browser || page) {
        if (isBridgeAlive()) await teardownBridge()
        else resetStaleBridge()
      }
      await launch()
      await openChatPage()
      lastStartError = null
    } catch (err) {
      lastStartError = err instanceof Error ? err.message : String(err)
      await teardownBridge()
      throw err
    }
  })()
  try { await starting } finally { starting = null }
}
```

**时序分析**：

1. **检查→赋值之间无 await**：
   - ① `if (starting) return starting` 和 ② `starting = (...)` 之间是纯同步代码，无 await。
   - **原子性完好**。

2. **复用判定移入 executor 的副作用**：
   - 旧代码：健康 bridge 上的并发调用在 ① 立即 return，不 join promise。
   - 新代码：健康 bridge 上的并发调用在 ① return（因为 `starting` 已设置），**不会**进入 executor。
   - **无副作用**：只有 `starting` 为 null 时才会进入 executor，此时是首次启动或失败后重试。

3. **executor 内二次判复用（③）**：
   - 在 `starting` 赋值后、executor 开始执行前，bridge 可能已被其他调用恢复。
   - ③ 捕获这个窗口，避免重复 launch。
   - **正确**：这是防御性编程，额外保护。

**结论**：`starting` 原子区完好，复用判定移入 executor 无副作用。Q1 **无问题**。

### Q2：teardownBridge 清 chatSessionId 是否让可恢复会话丢失？

**代码分析**：

```typescript
async function teardownBridge(): Promise<void> {
  const b = browser
  if (b) {
    try {
      await Promise.race([b.close(), sleep(CLOSE_TIMEOUT_MS)])
    } catch { /* 已死或关闭失败 */ }
  }
  killChromeTree()
  browser = null
  page = null
  chromeProc = null
  chatSessionId = null  // ← 这里清了 chatSessionId
}
```

**场景分析**：

1. **`openResumed()` 中途失败**：
   - `openResumed()` 在 `openChatPage()` 内调用。
   - 如果 `openResumed()` 抛错（如导航超时），catch 块执行后继续到 `dumpDom()` + `dropPersistedEntry()` + `chatSessionId = null` + `openHome()`。
   - 如果 `openHome()` 也抛错，则 `openChatPage()` 抛错，`startBridge()` catch 块执行 `teardownBridge()`。
   - 此时 `chatSessionId` 已被 `openResumed()` 清为 null，`teardownBridge()` 再次清（幂等）。

2. **关键时序**：
   - `openResumed()` 内部已清 `chatSessionId` 并清除持久化条目（`dropPersistedEntry`）。
   - `teardownBridge()` 的清操作是幂等的，不会额外丢失信息。

**结论**：`teardownBridge()` 清 `chatSessionId` **不会导致可恢复会话丢失**，因为：
- 如果 `openResumed()` 成功，`chatSessionId` 会被设为新值（成功恢复）。
- 如果 `openResumed()` 失败，内部已清 `chatSessionId` 并清除持久化条目。
- `teardownBridge()` 的清操作是幂等的。

Q2 **无问题**。

### Q3：3s close 超时落在同步路径上是否该挪到后台？

**代码分析**：

```typescript
async function teardownBridge(): Promise<void> {
  const b = browser
  if (b) {
    try {
      await Promise.race([b.close(), sleep(CLOSE_TIMEOUT_MS)])  // ← 最多等 3s
    } catch { /* 已死或关闭失败 */ }
  }
  killChromeTree()
  // ...
}

async function startBridge(): Promise<void> {
  starting = (async () => {
    try {
      // ...
    } catch (err) {
      lastStartError = ...
      await teardownBridge()  // ← 这里等最多 3s
      throw err
    }
  })()
  try { await starting } finally { starting = null }
}

async *generate(req): AsyncIterable<GenerateChunk> {
  await startBridge()  // ← 同步路径上
  // ...
}
```

**影响分析**：

1. **HTTP 请求路径**：
   - 客户端发送 `/v1/chat/completions` 请求。
   - 如果 bridge 处于「坏页」状态，`startBridge()` 会执行 `teardownBridge()`，最多等 3s。
   - **客户端需等待至少 3s** 才能收到 502 或正常响应。

2. **CLI 阻塞登录流程**：
   - CLI 启动时调用 `bridge.start()`，如果失败也会等 3s teardown。
   - **用户体验**：启动时多等 3s。

**是否该挪到后台？**

- **Arguments for moving to background**：
  - 3s 等待对实时性要求高的场景不友好（HTTP 请求、CLI 交互）。
  - `close()` 失败不会导致资源泄漏（`killChromeTree()` 会杀进程）。
  - 可以 async fire-and-forget teardown。

- **Arguments against**：
  - `teardownBridge()` 必须在 `throw err` 之前完成，否则 `browser` 可能仍为陈旧句柄，下次 `startBridge()` 误判为「活着」而永久早退。
  - 如果 teardown 在后台，`throw err` 先执行，调用方收到错误，但 `browser` 仍为陈旧句柄 → 下一次 `startBridge()` 的 `isBridgeAlive() && page` 判据可能返回 true（browser 活着但 page 为 null）→ 再次 502。
  - **关键**：teardown 必须在 `throw err` 之前完成，这是正确性要求，不是性能选择。

**结论**：3s 超时**不应该挪到后台**。teardown 必须在抛错前完成，否则下次启动会再次遇到「陈旧句柄」问题。这是正确性约束，不是性能优化空间。Q3 **无问题**。

### Q4：lastStartError 会不会造成信息泄漏？

**代码分析**：

```typescript
// health() 中
const idle = (): Health => (
  lastStartError
    ? { status: 'bridge_idle', loggedIn: false, error: lastStartError }
    : { status: 'bridge_idle', loggedIn: false }
)
```

**泄漏风险分析**：

1. `lastStartError` 存储的是 `err.message`，可能包含：
   - 文件路径（如 `D:\15812\...`）
   - Chrome 可执行文件路径
   - 选择器名称（如 `::-p-text(开启新对话)`）
   - DeepSeek 内部错误信息

2. `/health` 端点返回给**任何调用方**（运维探针、OpenCode、用户 curl）。

**评审判断**：

- 项目定位是「本地私有 shim」，监听 `127.0.0.1:8790`。
- 调用方是本地进程（OpenCode、CLI 脚本），不是外部网络。
- 信息泄漏风险**极低**（仅限本地用户可见）。
- 但作为最佳实践，建议：
  - 截断过长错误消息（如 >200 字符）。
  - 或只在 `LOG_LEVEL=debug` 时返回完整错误。

**结论**：当前实现可接受（本地服务，风险低）。建议后续优化（截断或日志级控制），**不阻塞**。

## 四、bridge_error 采纳问题（用户提问）

**用户说明**：你建议加 `bridge_error` 状态，**没有采纳**，改成在 `bridge_idle` 的可选 `error` 字段里捎带失败原因。理由：状态是给调用方做分支决策的，失败原因不是分支维度；新增 union 成员会破坏外部做 exhaustive switch 的消费者（OpenCode 等）。

**评审同意**。

**理由**：
1. `bridge_idle` 已准确描述「bridge 未就绪」的状态，调用方只需「等」或「重试」。
2. 失败原因是**诊断信息**，不是**决策维度**——调用方不需要根据失败原因做不同分支。
3. 新增 `bridge_error` 会破坏 TypeScript exhaustive switch 的消费者，这是真实兼容风险。
4. 可选 `error?: string` 字段是更优雅的设计：保持联合类型不变，同时提供诊断信息。

**结论**：**同意不采纳 `bridge_error`**。Q1 **无 blocker**。
