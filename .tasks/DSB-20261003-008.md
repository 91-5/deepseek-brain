## Review questions

1. **200 这个上限有依据吗？** 它是拍的。当前真实错误来源（`chromeNotFoundMessage`
   等）有多长？如果真实消息普遍短于 200，截断就是**永远不触发的死代码**——那我这
   4 项测试里的第 4 项是「人为造长路径」才绿的，与 COND-2 那条「有测试无判别力」
   是同类问题。请判断：留着一个当前不触发的防御，还是删掉等真需要时再加？
2. **`…(+N chars)` 本身泄露信息吗？** N 暴露了原始消息长度，而长度也是信息
   （可据此猜路径深度、URL 结构）。是否该固定化（例如统一写 `…(truncated)`）？
3. **「内存留全文、出口裁剪」这个分离，有没有反噬路径？** 例如日志把裁剪后的值
   记进去、或某天有人顺手把 `lastStartError` 赋成裁剪后的值。有没有更结构化的做法
   （比如拆成 `lastStartError` + `healthErrorView` 两个变量）？
4. **`.tasks/` 顶层只剩一张卡，会不会让后续 agent 检索不到历史？** 现在跨平台支持
   的三轮评审、006/007 两轮全在 `legacy/` 下，只能靠文件名和 `legacy/README.md` 找到。
   这是反膨胀的代价，但代价是否过大？
5. **索引桩的诚实边界够不够？** 我只写 verdict、计数、归属，没复原 blocker 内容。
   若你认为这仍不足以让「谁判了什么」可追溯，正确的收尾是什么——删掉无主的 verdict？
