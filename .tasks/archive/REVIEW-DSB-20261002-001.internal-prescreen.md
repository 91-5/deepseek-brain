## Review questions — point by point

1. **候选表生成可测、真实启动不可测；§6 是否诚实？有何遗漏？** 部分诚实，不完整。（大概率）spec §4.4 承认「测试仅覆盖候选表生成，不覆盖启动」，§6 列出 Linux/macOS 拉起、非 Windows 首登、无 display 失败模式四项不可验证——方向对。但遗漏见 B5：WSL2+WSLg、Unix X_OK 分支、Windows 真实启动同样未被新测试覆盖、`ProgramW6432` 真实语义四项未收录；且「✅ `probe()` 三平台行为」一句过度覆盖（Windows 上只验了退化分支）。修复成本低：§6 补四行 + 改 ✅ 为「Windows 退化分支已验，Unix 分支未验」。
2. **「显式值与探测复用同一判据」是否真被 `accessSync(X_OK)` 统一？有无第二真相？** 在 `chrome-detect.ts` 内成立，端到端不成立。（确定）第二真相有两条：(a) `src/cli.ts:72` 显式值零校验直通 vs `deepseek-web.ts:352` 显式值过判据——CLI 通过而 bridge 失败；(b) `spawn` + `puppeteer.connect` 的 OS 层校验（缺库、无 display、sandbox）在 `accessSync` 通过之后仍会失败，这是 `probe` 永远覆盖不了的启动期真相。spec 只统一了第一层，未处理 (a)，未承认 (b)。B2 修 (a)；(b) 应在 §6 加一行「`accessSync` 通过 ≠ 可启动」。
3. **Tier 表述是否过度承诺？README 是否仍暗示 macOS 可用？** 当前 README（改前）无 macOS 暗示——三处 `Windows only`（`README.md:9,220,222`）是硬拒绝，与 Tier 计划无冲突。（确定）风险在未来 README：Tier2「代码支持·未验证」的「支持」二字 + Tier3 加了 macOS 路径却写「不承诺」，用户极易读成「macOS 能用」。spec §3 的第一屏 headless 硬前提要求是对的，但 Tier 标签建议改「代码存在·未验证 / 实验性」，Tier3 改「路径已加入但完全未验证，首登能否成功未知，预期需 P2 真机验证」并配 `chrome-not-found` 之外的 spawn 失败说明。另 `package.json:4` description 须同步（B4），否则包页继续暗示 Windows-only，与 Tier 自相矛盾。
4. **删 `os` 是「更诚实」还是「转嫁复杂度」？** 方向是更诚实，诚实度取决于三处跟进。（大概率）删字段（vs 白名单 `["win32","linux"]` 主动拒绝 macOS）的理由成立：`os` 是安装期硬拒绝，不是能力声明，删的成本≈零而信息表达力由 README Tier 接管，比替用户做决定灵活。但若 B3（错误信息列错平台路径）、B4（description 残留）、无 display 下非优雅失败（spec §8 中风险的缓解项错配：`chrome-not-found` 早失败覆盖不了「找得到但起不来」的挂起）三处不跟进，实际效果就是把「装不上」的明确失败换成「装得上、首登挂起、报错还指错方向」的模糊失败——那即转嫁。本轮判断：删 `os` 本身 PASS，三个跟进项是诚实性的必要非充分条件，已记入 B3/B4/B5。
