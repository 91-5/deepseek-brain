## Context

本卡修的是你在 `DSB-20261002-006` 的 verdict 里给出的 **COND-1**（weak，非阻塞）：

> Q2: `openChatPage()` 失败后 bridge 可能陷入永久 `bridge_idle` 状态（browser 活着
> 但 page 为 null）。建议后续增加显式错误状态（如 `bridge_error`）。

机理比 verdict 描述的更具体，有两条独立的砖化路径：

1. `launch()` 成功但 `openChatPage()` 抛错（网络抖动 / DeepSeek 改版 / 会话文件损坏）
   → `browser` 仍 connected、`page` 为 null → `isBridgeAlive()` 为 true 让
   `startBridge()` **永久早退** → 每个请求撞 `bridge not started` 而 502，**永不重试**。
2. `openChatPage()` 里 `page = ...newPage()` 的赋值在 `goto`/`openHome()` **之前**，
   所以导航失败时 `page` **非 null 却是坏页**。这一条连「判 page 是否为 null」的修法
   也抓不到——判据若只看存活或只看 null，都会漏掉坏页，于是等不到 textarea，
   15s 后 502 且永不重试。

同时 `/health` 报 `bridge_idle`（本意「还没被叫醒，等一下」），把「启动失败」说成
「在等」，运维据此既等不到好、也查不到原因。

## Review questions

1. **`starting` 原子区是否仍然完好？** 外层现在只剩 `if (starting) return starting`，
   复用判定也被移进 executor。这满足了「检查→赋值之间无 await」吗？把判定移进去
   是否带来副作用——健康 bridge 上的并发调用现在都要 join promise，而此前是立即 return？
2. **`teardownBridge()` 清 `chatSessionId` 是否过头？** 若失败发生在 `openResumed()`
   中途（已部分恢复会话），清掉 id 会让下次 `start()` 走 `openHome()` 而非深链恢复，
   可恢复会话就丢了。这是不是应该保留？
3. **3s `close()` 超时落在用户请求的同步路径上**（generate → startBridge → teardown）。
   对 CLI 的阻塞登录流程和 HTTP 请求分别意味着什么？首次失败后的 teardown 是否该挪到
   后台，不阻塞这一次响应？
4. **`lastStartError` 会不会造成信息泄漏？** 它把内部错误消息（可能含路径、选择器名）
   通过 `/health` 的响应体公开给任何探针。是否需要截断或只在本地日志里保留？
5. **「部分红」的敏感性可接受吗？** 见 A9：3 项测试只有 1 项真正对旧代码敏感。
   另两项在旧代码下也通过——它们是「诚实但非判别」的断言。按你的门禁标准，
   这种「有测试但无判别力」的状态该判 condition 还是 blocker？
6. **本卡该不该合？** 考虑到核心机理（坏页路径）无自动化覆盖，你是否要求先补
   puppeteer 注入点再合入？
