## 二、评审问题回答

### Q1：isConnected() 探测时机是否正确？重复 launch 风险？

**代码分析**：

```typescript
async function startBridge(): Promise<void> {
  if (starting) return starting           // ① 幂等锁：已有启动任务则复用
  if (isBridgeAlive()) return             // ② 存活则早退
  if (browser || page) resetStaleBridge() // ③ 清陈旧句柄
  starting = (async () => {
    await launch()
    await openChatPage()
  })()
  try { await starting } finally { starting = null }
}
```

**时序分析**：

1. **Chrome 正在启动中**（`launch()` 调用 `retryConnect`，最多 15 次 × 1s = 15s）：
   - `isBridgeAlive()` 在 `launch()` 完成前会抛异常（连接未建立），`try/catch` 返回 false。
   - 但此时 `starting` 不为 null，`generate()` 调用 `startBridge()` 会命中 ① 返回同一个 promise，不会重复 launch。
   - 如果两个并发调用同时在 ① 之前进入（`starting` 仍为 null）：
     - 第一个调用设置 `starting` 并开始 launch。
     - 第二个调用在 `starting` 已设置后进入，命中 ① 返回同一个 promise。
     - **不会重复 launch**。

2. **Chrome 刚启动但 isConnected() 尚未返回 true 的窗口**：
   - `retryConnect` 内部有 15 次重试，每次间隔 1s。
   - 在此期间 `isBridgeAlive()` 返回 false，但 `starting` 已设置，并发调用会被 ① 拦截。
   - **不会重复 launch**。

3. **launch() 成功后**：
   - `browser` 被赋值，`isConnected()` 返回 true。
   - `starting` 在 `finally` 块中置 null。
   - 后续调用命中 ② 早退。

**结论**：`starting` promise 的幂等锁**足以覆盖**并发窗口，不需要额外的 `launching` 标志。Q1 **无阻塞性问题**。

### Q2：显式 null 收窄是否掩盖 launch 失败？

**代码路径**：

```typescript
// health() 中
if (!isBridgeAlive()) return { status: 'bridge_idle', loggedIn: false }
if (!page) return { status: 'bridge_idle', loggedIn: false }  // ← 这里
```

**场景分析**：

- `isBridgeAlive()` 返回 true → `browser` 非 null 且 `isConnected()` 为 true。
- `page` 为 null 的可能情况：
  1. `launch()` 成功但 `openChatPage()` 尚未完成（`starting` 任务仍在进行）。
  2. `openChatPage()` 抛出异常，`starting` 任务未完成，`page` 仍为 null。

**情况 1**（启动中）：
- `health()` 返回 `bridge_idle`，调用方等待。
- 下一次 `health()` 调用时，`openChatPage()` 可能已完成，`page` 非 null，返回 `ok` 或 `login_required`。
- **语义正确**：启动中是正常状态，不是故障。

**情况 2**（`openChatPage()` 失败）：
- `starting` 任务抛异常，`try/finally` 使 `starting = null`。
- `browser` 已赋值（`launch()` 成功），`page` 为 null。
- 下次 `health()` 调用：`isBridgeAlive()` 返回 true，`page` 为 null → 返回 `bridge_idle`。
- 下次 `generate()` 调用：`isBridgeAlive()` 返回 true，但 `page` 为 null → 抛出 `Error('bridge not started')`。
- **问题**：`bridge_idle` 持续返回，但 `generate()` 会抛出错误。调用方可能无限等待 `bridge_idle` 转为 `ok`，但实际 `openChatPage()` 已失败，不会自动恢复。

**这是真实风险**：如果 `openChatPage()` 内部错误（如导航超时、选择器失效），`bridge` 会陷入「browser 活着但 page 为 null」的永久 `bridge_idle` 状态，直到进程重启。

**但**：
- `openChatPage()` 内部有 `try/catch` + `dumpDom()` 日志，会记录失败原因。
- `retryConnect` 在 `launch()` 中有 15 次重试，降低了连接失败概率。
- 这是边缘情况，且日志会暴露问题。

**结论**：Q2 是**weak condition**——理论上存在启动失败后永久 `bridge_idle` 的可能，但概率低且有日志可查。建议后续增加 `openChatPage()` 失败的显式错误状态（如 `bridge_error`），但不阻塞本次评审。
